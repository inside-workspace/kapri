## 1. Introduction

### 1.1 Purpose

This specification defines the reference interoperability tests for implementations conforming to the KAPRI Specification Suite.

The purpose of these tests is to verify that independently developed implementations can generate, exchange, validate and process Knowledge Asset Packages consistently.

Successful interoperability demonstrates that implementations can interact without implementation-specific knowledge beyond the KAPRI specifications and an agreed Cryptographic Profile.

### 1.2 Scope

This specification defines:

- interoperability testing between independent implementations,
- Reference Package processing,
- cross-implementation Package exchange,
- comparison of Technical Validation results,
- interoperability testing of Secure Delivery.

This specification does not define:

- implementation-specific optimizations,
- transport protocols,
- deployment environments,
- performance benchmarks,
- organizational trust policies,
- authorization policies.

### 1.3 Relationship to Other Specifications

This specification forms part of the KAPRI Conformance Test Suite.

It verifies interoperability between implementations conforming to:

- S0 – Knowledge Asset Package Architecture Specification
- SC0 – Common Serialization Rules
- SC1 – Common Data Types
- S1 – Package Manifest Schema
- S2 – Packing List Schema
- S3 – Composition Schema
- S4 – KAP Key Delivery Message Schema
- T0 – Conformance Test Architecture
- T1 – Public Key Infrastructure
- T2 – Package Generation
- T3 – Package Validation
- T4 – Secure Delivery

Cryptographic interoperability SHALL be tested using a Cryptographic Profile supported by all participating implementations.

The Reference Cryptographic Profile is defined by T1 – Public Key Infrastructure (PKI).


# 2. Interoperability

## 2.1 Purpose

Interoperability verifies that independent implementations can exchange and process Knowledge Asset Packages according to the same normative specifications.

Interoperability does not require implementations to produce byte-identical Packages.

Different implementations MAY use different internal architectures, programming languages and processing models.

They SHALL preserve the structures, semantics and validation behavior defined by the KAPRI Specification Suite.

## 2.2 Interoperability Model

Interoperability SHALL be tested in two complementary ways:

### Reference Interoperability

Each implementation processes the same KAPRI Reference Package and produces the applicable Technical Validation results.

### Cross-Implementation Interoperability

A Package generated by one implementation is processed and validated by another implementation.

For two implementations A and B, the basic interoperability relationship is:

```
Implementation A
        │
        │ generates
        ▼
     Package A
        │
        ▼
Implementation B
 validates/processes
     Package A


Implementation B
        │
        │ generates
        ▼
     Package B
        │
        ▼
Implementation A
 validates/processes
     Package B
```

Where Secure Delivery is tested, recipient-specific KAP-KDMs SHALL also be exchanged and processed across implementations.

## 2.3 Interoperability Workflow

The reference interoperability workflow SHALL consist of the following steps:

```
Process Reference Package
        ↓
Generate Implementation Package
        ↓
Exchange Package
        ↓
Validate Exchanged Package
        ↓
Validate Secure Delivery
        ↓
Compare Technical Validation Results
        ↓
Determine Interoperability
```

Secure Delivery testing applies only where encrypted Package Files are included in the interoperability test.

## 2.4 Interoperability Responsibilities

The interoperability process SHALL verify that:

- independently generated Packages conform to the KAPRI Specification Suite,
- Packages generated by one implementation can be processed by another conforming implementation,
- mandatory Package components are interpreted consistently,
- Package references and integrity relationships are interpreted consistently,
- digital signatures are validated consistently,
- certification chains are validated consistently,
- cryptographic operations use a mutually supported Cryptographic Profile,
- recipient-specific KAP-KDMs are interpreted consistently where Secure Delivery applies,
- Encrypted File Keys can be recovered by the intended Recipient where Secure Delivery applies,
- independent implementations produce equivalent results for applicable deterministic Technical Validation categories defined by S0.

Recipient Decisions are not required to be equivalent between implementations.

Differences resulting solely from local trust policies, Product Support or Version Compatibility SHALL NOT by themselves constitute an interoperability failure.


# 3. Conformance Tests

The reference interoperability process SHALL provide the following executable conformance tests.

| Test | Purpose |
| --- | --- |
| T5.1 | Process KAPRI Reference Package |
| T5.2 | Generate Implementation Package |
| T5.3 | Exchange Package |
| T5.4 | Validate Exchanged Package |
| T5.5 | Validate Secure Delivery |
| T5.6 | Compare Technical Validation Results |
| T5.7 | Determine Interoperability |

## T5.1 Process KAPRI Reference Package

Each participating implementation SHALL process the KAPRI Reference Package.

The implementation SHALL perform all applicable Technical Validation defined by S0 and T3.

**Expected result:** The implementation successfully processes the Reference Package and produces the expected Technical Validation results.

## T5.2 Generate Implementation Package

Each participating Producer implementation SHALL generate a Knowledge Asset Package according to T2 – Package Generation.

The generated Package SHALL conform to the applicable normative specifications.

The Package does not need to be byte-identical to the KAPRI Reference Package.

**Expected result:** Each Producer generates an independently created conforming Knowledge Asset Package.

## T5.3 Exchange Package

Each independently generated Package SHALL be provided to at least one other participating implementation.

The exchange mechanism is outside the scope of this specification.

The Package SHALL be transferred without modification.

**Expected result:** The receiving implementation can access and process the Package without implementation-specific transformation.

## T5.4 Validate Exchanged Package

The receiving implementation SHALL validate the exchanged Package according to T3 – Package Validation.

All applicable Technical Validation categories defined by S0 SHALL be evaluated.

**Expected result:** A conforming Package generated by one implementation successfully passes Technical Validation by another implementation.

## T5.5 Validate Secure Delivery

Where the exchanged Package contains encrypted Package Files, Secure Delivery SHALL be tested according to T4 – Secure Delivery.

A recipient-specific KAP-KDM generated by one implementation SHALL be processed by another implementation using the corresponding Recipient Private Key.

**Expected result:** The receiving implementation successfully validates the KAP-KDM, recovers the File Keys and decrypts the corresponding Package Files.

Where the Package contains no encrypted Package Files, this test is not applicable.

## T5.6 Compare Technical Validation Results

Technical Validation results produced by participating implementations SHALL be compared.

For the same Package and the same applicable Cryptographic Profile, implementations SHALL produce equivalent results for deterministic Technical Validation categories defined by S0.

Equivalent results do not require identical internal representations or output formats.

They require equivalent semantic validation outcomes.

Recipient Decisions SHALL NOT be included in the equivalence requirement.

**Expected result:** Participating implementations produce semantically equivalent Technical Validation results.

## T5.7 Determine Interoperability

Interoperability SHALL be established where:

- the KAPRI Reference Package is successfully processed,
- independently generated conforming Packages are successfully processed by another implementation,
- applicable Technical Validation produces equivalent results,
- applicable Secure Delivery operations can be performed across implementations,
- the semantics defined by the KAPRI Specification Suite are preserved.

**Expected result:** The participating implementations are interoperable for the tested capabilities and Cryptographic Profile.


# 4. Test Execution Order

The interoperability tests SHALL be executed in the following order:

```
T5.1 Process KAPRI Reference Package
        ↓
T5.2 Generate Implementation Package
        ↓
T5.3 Exchange Package
        ↓
T5.4 Validate Exchanged Package
        ↓
T5.5 Validate Secure Delivery
        ↓
T5.6 Compare Technical Validation Results
        ↓
T5.7 Determine Interoperability
```

T5.5 applies only where encrypted Package Files are included in the interoperability test.

Each applicable test depends on the successful completion of all required preceding tests.


# 5. Expected Results

The interoperability process SHALL demonstrate that:

- independently developed implementations can process the KAPRI Reference Package,
- independently developed Producers can generate conforming Knowledge Asset Packages,
- Packages generated by one implementation can be processed by another implementation,
- mandatory Package components and their semantics are interpreted consistently,
- equivalent Technical Validation results are produced for the same Package,
- cryptographic validation produces equivalent results when using the same Cryptographic Profile,
- recipient-specific Secure Delivery can be performed across implementations where applicable,
- implementation technology does not affect the semantic interpretation of the Package.

Interoperability SHALL NOT require equivalent Recipient Decisions where those decisions depend on local trust policies or implementation capabilities.


# 6. Conformance

An implementation claiming conformance with this specification SHALL:

- successfully process the KAPRI Reference Package,
- generate conforming Knowledge Asset Packages for all capabilities it claims to support,
- successfully process conforming Packages generated by another implementation,
- produce equivalent Technical Validation results for the same Package and applicable Cryptographic Profile,
- successfully perform applicable cross-implementation Secure Delivery tests,
- preserve the structures and semantics defined by the KAPRI Specification Suite.

Conformance SHALL be stated for the capabilities and Cryptographic Profile covered by the interoperability test.
